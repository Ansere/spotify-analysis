# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the app

```bash
source ~/venv/bin/activate
pip install -r requirements.txt
python serve.py          # serves at http://127.0.0.1:8765/
```

To regenerate `dashboard.html` without starting the server:

```bash
python build_dashboard.py
```

To run the test suite (no dependencies beyond the project itself):

```bash
python test_merge_dedup.py
python test_lastfm.py      # Last.fm helpers; no network or key needed
python test_genres.py      # Genre classification; synthetic fixtures
```

Spotify refresh requires a Spotify app Client ID. Set it in `.env`:

```
SPOTIFY_CLIENT_ID=your_client_id_here
```

Create the app at https://developer.spotify.com/dashboard and add `http://127.0.0.1:8765/callback` as the redirect URI with the Web API checkbox enabled.

`serve.py` also respects `REFRESH_BIND_HOST` (default `127.0.0.1`) and `REFRESH_PORT` (default `8765`) env vars.

For cloud sync, also set in `.env`:

```
DATA_REPO=yourname/spotify-analysis-data
DATA_REPO_TOKEN=your_github_pat
```

For artist tags and Last.fm similar-artist links, set a read-only Last.fm API key (https://www.last.fm/api/account/create, callback URL blank) and fill the cache once:

```
LASTFM_API_KEY=your_key
python lastfm_sync.py    # ~2 requests/artist above the play threshold; later Rescrapes top up 100 stale artists
```

`DATA_REPO_TOKEN` needs **Contents: Read and write** permission — it's used both to pull and to push the live buffer back after a local refresh.

## Architecture

Python modules, no database — all state lives in local JSON files.

**`build_dashboard.py`** — data pipeline. Reads all `music-history/Streaming_History_Audio_*.json` files, computes aggregate statistics (per-day/month/year series, top artists/tracks/albums, heatmap, streak, etc.), serializes the result to a JSON bundle, then injects it into `template.html` by replacing the `__DATA_JSON__` placeholder string. Output is `dashboard.html`. This file is auto-rebuilt by `serve.py` whenever source JSON or `template.html` is newer.

**`spotify_sync.py`** — Spotify API layer. Implements PKCE OAuth (no client secret), fetches the 50 most recently played tracks via `/v1/me/player/recently-played`, maps them to Extended Streaming History-shaped rows, deduplicates by `(ts, spotify_track_uri)` key, and atomically appends new rows to `Streaming_History_Audio_live.json`. Credentials are read from `.env` (`SPOTIFY_CLIENT_ID`) or `spotify_config.json`. Tokens are cached in `spotify_tokens.json` (chmod 600, atomic write).

**`art_sync.py`** — Fetches real Spotify album art and artist photos for the current top ~12 artists/albums/tracks (by minutes played), for the Rankings podium. Uses `/v1/search` (name + artist query) rather than direct id lookups — `/v1/tracks` and `/v1/artists` return 403 under this app's current Spotify API access tier, but Search remains available and returns the same image data. Reuses `spotify_sync.ensure_access_token()` for auth. Caches results to `art_cache.json` (gitignored), keyed `artist:<lowercased name>` / `album:<canon_album_key>` / `track:<canon_track_key>`. Best-effort like `cloud_pull.py`: failures are logged and returned as `(False, msg)`, never raised, so a refresh never breaks because art couldn't be fetched.

**`lastfm_sync.py`** — Fetches Last.fm `artist.getSimilar` and `artist.getTopTags` for artists meeting `GRAPH_MIN_PLAYS`, up to `GRAPH_ARTIST_CAP` and caches them in `lastfm_cache.json` (gitignored), keyed `artist:<lowercased name>` -> `{name, tags, similar: [[name, match], ...], fetched}`. Spotify's related-artists endpoint is closed to new apps (403), so Last.fm stands in for it. Tags are cleaned (generic/year/self-named tags dropped, top 5 with weight >= 20). Entries refresh after 30 days. Best-effort like `art_sync.py`: returns `(False, msg)` and never raises; skipped when `LASTFM_API_KEY` is unset.

**`serve.py`** — Flask server. Routes:
- `GET /` — serves `dashboard.html`, triggering a rebuild if stale
- `GET /callback` — receives the OAuth code from Spotify and puts it on `oauth_code_queue`
- `POST /api/pull` — pulls the live buffer from the data repo (if configured) then rebuilds the dashboard. Does NOT call the Spotify API. Triggered by the "Refresh" button.
- `POST /api/refresh` — always runs `cloud_pull.pull_live()` (if configured), then `spotify_sync.sync_incremental()`, then `art_sync.refresh_art_cache()`, then `lastfm_sync.refresh_cache()`, then `build_dashboard.main()`, then `cloud_pull.push_live()` (if configured), under a combined threading lock + PID-based file lock (`.refresh.lock`). Operates locally even without cloud credentials. Triggered by the "Rescrape" button.
- `POST /api/authorize` — forces a fresh Spotify PKCE login, stores the new refresh token locally, and pushes it to the data repo. Triggered by the "Re-authorize" button.
- `GET /api/refresh/status` — reads `.refresh.last.json` for last refresh result

**`template.html`** — HTML shell for the dashboard. References `dashboard.js` and `dashboard.css` via `<script src>` / `<link rel>` tags. `build_dashboard.py` injects only the `__DATA_JSON__` blob; charting logic lives in the external JS/CSS files, which Flask serves via `/dashboard.js` and `/dashboard.css` routes. Chart.js is loaded from CDN at runtime (`cdn.jsdelivr.net`); all other charting logic is local.

**`dashboard.js`** — All client-side rendering. Reads `DATA` from a `<script id="dash-data">` tag injected by `build_dashboard.py`. Day-offset arithmetic mirrors the Python bundle: `dayStrToOff` converts calendar dates to integer offsets from `DAY_EPOCH`, so JS and Python indexes stay in sync. Builds Chart.js charts for day/month/year series, heatmap, platform breakdown, and top artists/tracks/albums with a shared date-range filter.

**`dashboard.css`** — All styling for the dashboard.

**`cloud_pull.py`** — Four functions: `pull_exports()` downloads any yearly `Streaming_History_Audio_*.json` export from the data repo that is missing locally or differs by git blob SHA (so uploading a new export file to the data repo is enough; both the Refresh and Rescrape buttons call it before `pull_live()`; `python cloud_pull.py` runs both by hand), plus: `pull_live()` pulls the live JSON buffer from the private data repo (GitHub Contents API, with fallback to Git Data API for files >1 MB) into `music-history/Streaming_History_Audio_live.json`; `push_live()` writes the updated buffer back to the data repo after a local sync (uses Git Data API blob/tree/commit to handle files >1 MB); `push_live_token()` rotates the `live_token.json` in the data repo after a token refresh. All four are best-effort: if `DATA_REPO` / `DATA_REPO_TOKEN` are unset or the call fails, they log a warning and return `(False, msg)` without raising.

**`cloud_sync.py`** — Headless orchestrator for the GitHub Actions hourly scrape. Reads the Spotify refresh token from the data-repo checkout (`live_token.json`), calls `spotify_sync` to fetch new plays, and writes the updated live buffer and rotated token back so the workflow can commit them atomically. Env vars: `SPOTIFY_CLIENT_ID`, `SPOTIFY_HISTORY_DIR` (path to the data-repo checkout). Exit code 1 means the refresh token is expired and needs re-authorization locally.

## Key conventions

- **Display timezone**: `DISPLAY_TZ = ZoneInfo("America/Chicago")` in `build_dashboard.py`. All user-facing day/month/year buckets and the heatmap use this zone, not UTC.
- **Track/album deduplication**: `canon_track_key` and `canon_album_key` normalize to lowercase and join with `\x01` as separator, collapsing duplicate Spotify URIs for the same title+artist.
- **Extended history JSON vs. live JSON**: All `Streaming_History_Audio_*.json` files live in `music-history/`. Year-based export files are read-only; only `Streaming_History_Audio_live.json` is written by `spotify_sync.py`. The export files are authoritative for any period they cover — `load_events()` drops live rows whose timestamps fall within the export coverage window (plus a 4-second buffer) before running dedup. This prevents double-counting: Spotify's recently-played API reports `played_at` 0–3 seconds later than the data export records the same play, so exact `(ts, uri)` dedup fails to merge them.
- **Day index compression**: `build_dashboard.py` encodes the global `day_series` as `{"i": <days_since_epoch>, "ms": ..., "n": ...}` where the epoch is the calendar date of the first ever play. Per-entity daily data (artists/tracks/albums) uses `compact_days()`, which encodes as `[[i, ms, n], ...]` (3-element lists). JS's `dayOffFromSeriesRow` handles both formats transparently.
- **`is_music_stream()` filter**: Rows with `spotify_episode_uri` (podcasts) or `audiobook_uri` are excluded from all stats. Export JSONs can contain mixed content despite the "Audio" filename.
- **No per-entity data caps**: Every artist, track, and album gets its per-day array included in the bundle (previously capped at the top 2500/2600/1400 by `ms_played`; the caps were removed since they made the "in window" KPI tiles undercount on large histories).
- **Live row `ms_played` resolution**: The Spotify recently-played API returns track duration, not actual listening time. `resolve_live_ms_played()` post-processes unresolved rows (those with `ms_played_resolved: false`) by computing the time delta between consecutive `played_at` timestamps, capped at track duration. Rows already resolved (`ms_played_resolved: true`) are used as reference points but are not modified. This runs automatically after every sync.
- **Background automation (macOS)**: `com.USERNAME.spotify-serve.plist` in the repo root is a launchd agent that keeps the Flask server running. Replace `USERNAME` with your macOS username and load it into `~/Library/LaunchAgents/`. There is no longer a local hourly refresh plist — cloud-side scraping is handled entirely by the GitHub Actions workflow triggered by cron-job.org.
- **GitHub Actions**: `.github/workflows/spotify-sync.yml` runs `cloud_sync.py` on `workflow_dispatch` only — triggered hourly by cron-job.org via the GitHub API (`POST /repos/warithr621/spotify-analysis/actions/workflows/spotify-sync.yml/dispatches`). The cron-job.org PAT needs **Actions: Read and write** on `spotify-analysis` only. Required secrets: `SPOTIFY_CLIENT_ID`, `DATA_REPO_PAT` (Contents: Read and write on `spotify-analysis-data`). Required var: `DATA_REPO`. Optional var: `SPOTIFY_AUTH_DATE` (YYYY-MM-DD of last local re-auth, used to warn when the token nears 180-day expiry).
- **Stale rebuild trigger**: `maybe_rebuild_dashboard()` in `serve.py` compares `dashboard.html` mtime against `template.html` and the newest `music-history/*.json` file — rebuilds automatically on `GET /` if any source is newer.
- **API coverage limit**: `spotify_sync.py` fetches from `/v1/me/player/recently-played` with a cursor-based `after` parameter. The API window is ~50 items per page and covers roughly the last 50 plays Spotify has synced. Offline plays appear only after the device reconnects and syncs to Spotify's servers; if many plays accumulated while offline, plays outside the API window may be missed and must come from a Spotify Extended Streaming History export.
- **Rankings layout**: The Rankings section renders three full-width cards (Artists/Albums/Tracks), each a stepped 2nd/1st/3rd podium (top 3, with art) above a scrollable compact list (rank 4+, no art, sticky header). Columns differ by category but are always exactly 3 data fields beside the rank number — Artists: Name/Streams/Minutes; Albums: Album/Artist/Minutes; Tracks: Track/Artist/Minutes (Minutes mode; see Minutes/Plays toggle below for the Plays-mode layout). Rendered by `renderRankSection()` in `dashboard.js`; the search box filters by toggling element visibility (`applySearchVisibility()`) rather than rebuilding the DOM or re-ranking.
- **Minutes/Plays toggle**: The switch fixed top-right below Rescrape (`#metric-switch` in `template.html`) flips a module-level `metric` var in `dashboard.js` between `"minutes"` (default) and `"plays"`, then calls `rebuildRankings()`. It only affects the Rankings section — KPI tiles, the artist-dive chart, and the artist datalist still rank/sort by minutes regardless of the toggle. `rankArtists`/`rankTracks`/`rankAlbums` take a `metric` param that changes the sort key (`fm` minutes-ms vs `fn` play count). In Plays mode: for artists, the podium's 2nd row becomes plain minutes (no `fmtMin` day/hour hint) and the 3rd row becomes streams, and the list table swaps its Streams/Minutes columns to match (`updateRankHeaders()` relabels the `#hd-artists-2`/`#hd-artists-3` header cells); for albums/tracks, the minutes stat is replaced outright by streams in both the podium and the list column (`#hd-albums-metric`/`#hd-tracks-metric` header relabels to "Streams"). `minutesCellHtml(ms, showHint)` and `streamsCellHtml(n)` are the shared cell renderers behind both modes.
- **Art cache**: `art_cache.json` (gitignored, like `dashboard.html`) maps `artist:<name>` / `album:<key>` / `track:<key>` to a Spotify CDN image URL. Populated by `art_sync.py` (see Architecture); `build_dashboard.py` reads it read-only via `load_art_cache()` and attaches an `image` field to each artist/track/album entry in the bundle when cached. Entities without cached art fall back to a colored initial-letter tile in the frontend (`artHtml()` in `dashboard.js`).
- **Top listens race** (`dashboard.js`, `race` state, `#c-race`): canvas line race, one line per artist/track/album, value = minutes in the trailing 7/30/90 days or cumulative ("All time"). Only each day's top 10 are drawn; the y-scale is eased but never below the true visible peak; playback starts 3 days before the first visible listen (`data.start`). Filters: artist chips (only/hide; tracks and albums filter by their artist) and an optional Last.fm tag. Candidate pools cover all entities; only candidates reaching a daily top list get dense series.
- **Artist web** (d3 force graph, `#artist-web`): nodes are the top artists in the date range. Links come from Last.fm similarity (`lastfm_links`, static `[i, j, match]` pairs) or from shared listening sessions (`artist_sessions`: `[day_index, [artist_idx...]]`, sessions split at 30-minute gaps, artists meeting the graph play threshold only). Node color is the artist's top Last.fm tag, or a link cluster. Artist index `i` is also the index into `DATA.artists`.
- **Taste map** (`tasteMap` state, `#c-map`): canvas map of the artists meeting the graph play threshold. Positions come from a one-off d3 force layout over `lastfm_links` plus a weak same-top-tag pull (`tasteLayout()`, deterministic, fit to the 2nd-98th percentile). Time lights the map up: "Everything heard so far" (dots appear with a pulse at each artist's first listen in the filtered range) or "Last 30 days". Hidden until `lastfm_links` exist.
- **Animation speed**: the speed dropdowns on all three animations (line race, taste map) set the *length* of the whole animation in seconds (90/45/20/10), so playback rate is `playable span / seconds` and short date ranges play slower per day.
- **Taste map overlays** (`tasteMap.overlay`): *Trail: last 30 days' center* draws the day-by-day centre of mass of the previous 30 days of listening (per-artist trailing weights x layout positions, smoothed); *Trail: all-time center* does the same with cumulative totals, so it drifts slowly; *Glow explored territory* lights soft halos around every artist heard so far, so the dark gaps are unexplored regions.
- **Daily map walk** (`walk` state, `#c-walk`): hops a dot between artists play-by-play for one day or week. Data is `map_walk` in the bundle: `[day_index, [minute_of_day, artist_idx, ...]]`, plays >= 30 s by the artists meeting the graph play threshold only, in Chicago local time. Speeds set the total walk length (60/30/15 s), not plays per second.
- **Line race views**: the View dropdown's first entry follows the global Minutes/Plays toggle (`raceView()`); the others are `% of all listening` (share of total minutes or plays), `Listening streak` (current consecutive days played) and `Longest #1 streak` (running max of consecutive days as that day's most-played). Streak views ignore the time-window dropdown.
- **Minutes/Plays toggle scope**: it now re-renders all charts (`renderCharts()`): month/year/artist charts, the line race, taste map dot sizes, and artist-web node sizes. KPI tiles still always use minutes.
- **Animation defaults and controls**: the line race and taste map no longer autoplay; each rests on its final frame and Play starts it from the beginning (`racePlay()` etc. restart when already at the end). Every animated card gets a Full screen button from `wireFullscreen()` (Fullscreen API, falling back to a fixed-position `.is-fullscreen` class). The line race draws a "#1 streak" panel in its top-right corner: how many consecutive days the current #1 has topped the chart, plus the record so far in the range (`data.leaders` / `streakLen` / `recLen`).
- **Daily heatmap** (`renderHeatmap()`, `#heat-host`): GitHub-style SVG calendar, one block per year (newest first), one cell per day, shaded by plays or minutes per the Minutes/Plays toggle on a sqrt scale capped at the 95th percentile. Days outside the date filter are greyed. Clicking a day loads it into the Daily map walk.
- **Taste map colours**: dots are coloured by the artist's top Last.fm tag; the colour key is the `#map-legend` row (the old in-canvas tag names were removed).
- **Taste river** (`renderRiver()`, `#river-host`): d3 streamgraph (wiggle offset, inside-out order) of the top 8-24 Last.fm tags, monthly buckets for ranges over ~8 months (weekly otherwise); partial edge buckets are trimmed. An artist counts toward each of its tags, so streams overlap. Follows the Minutes/Plays toggle and the date filter.
- **Compare two periods** (`renderCompare()`, `#c-cmp`): taste map dots coloured by how each artist's *share* of listening moved from period A (blue) to period B (orange), with a dashed arrow between the two periods' centres of mass and "Moved into / Left behind" lists. It uses its own date inputs (presets or custom) and ignores the page's date filter.
- **Daily map walk, all time**: the span dropdown's "All time" walks every play by the artists meeting the graph play threshold (with no fixed play-count limit). Counts are kept incrementally (`walkCounts()`), the trail grows with playback rate, and Epic/Marathon speeds (2 and 5 min) exist because 30 s is a blur at that size. Animation frame steps are clamped to be non-negative: a first-frame timestamp earlier than `performance.now()` used to push the position below 0 and kill the loop.
- **Dev server**: `serve.py` refuses to start if its port is already taken (on Windows, Werkzeug's SO_REUSEADDR lets duplicate servers share a port, and a stale one would rebuild `dashboard.html` with old code), reloads `build_dashboard` before every rebuild, and treats `build_dashboard.py` and the art/Last.fm caches as rebuild triggers.
- **All artists everywhere**: `GRAPH_ARTIST_CAP` is now effectively unlimited, so the session graph, map walk, Last.fm links, taste map, compare view and river cover every artist (artist index `i` is still the index into `DATA.artists`). Two things make that tractable: (1) the taste map layout runs in a Web Worker (`ensureTasteLayout()`, the same `tasteRunSim()` is stringified into the worker, with a main-thread fallback) and the result is cached in `localStorage` under `taste-layout:v1:...` keyed by node/link counts and a link checksum, so subsequent loads can reuse the layout; (2) per-artist data on the map is sparse (`data.days` / `data.cum` per artist, one sweep for the centres of mass) instead of dense per-day arrays. `lastfm_sync.py` fetches with 4 threads behind a shared 5 req/s limiter; run `python lastfm_sync.py` once for the long tail, progress is saved every 100.
- **Line race scales to everything**: `raceCandidates()` sweeps every artist/track/album/tag once (events bucketed by day, trailing sums updated as they enter and leave) to find who ever reaches a day's top list; only those get dense series. The old per-kind pool caps are gone.
- **Long-tail cut**: only artists with at least `GRAPH_MIN_PLAYS` (3) plays go into the session graph, walk, Last.fm links/fetch, taste map, compare and river. `build_dashboard.py` sorts those artists first (by minutes) so they are a prefix of `DATA.artists` and `graph_artist_cap` is the prefix length; the rest still appear in rankings and the line race, which covers every artist. `lastfm_sync.py` applies the same cut when choosing whom to fetch.
- **Taste map colour setting** (`tasteMap.color`): *top tag* uses each artist's first Last.fm tag (the 14 commonest get colours, the rest grey). *Recency of listening* colours each artist by the minutes/plays-weighted average date of its listening **up to the current animation date**, mapped linearly onto the fixed timeline (indigo -> fuchsia -> orange -> yellow), so the colour is the colour of that date on the time slider and yellow only appears once the animation reaches late dates. *Recency, ranked* uses the same weighted average date but ranks it against the other artists heard so far, so the whole ramp is always in use and dots cool relative to everyone else. Both come from `tasteRecencyColors(data, t, mode)` (per-artist running sums `data.cum` / `data.cumDV`, cached per day). The time slider's track is painted with the matching key (`data.gradient` for recency, `data.gradientRank` for ranked; `#map-scrub.colored`) and `renderTasteLegend()` swaps the legend.
- **Taste map pan/zoom** (`tasteMap.zoom`): wheel zooms about the cursor, dragging pans, double-click or Reset view restores it. `tasteXY()` applies the zoom on top of the fitted view and no longer clamps points to the canvas edge (the walk and compare canvases still clamp via `tasteProject(..., clamp=true)`); the fit ignores the outermost 1% either side. Dots and glows grow gently with zoom (`tasteDotScale()`). All tooltips go through `placeTip()`, which flips/clamps them inside their container; map name labels are clamped onto the canvas.
- **Taste map labels and undiscovered artists**: the Labels dropdown is artist names / genres / both / none. Genre labels (`layout.regions`) put each of the 14 commonest top tags at the minutes-weighted centre of its artists (needs >= 4), drawn faintly behind the dots in Inter and scaled with zoom. `tasteMap.ghosts` is *dim* (artists not yet heard show as faint dots) or *hide* (they are not drawn at all and cannot be hovered, so the map fills in from empty as time passes).
- **Interactive walk and compare maps**: both canvases now share `wirePanZoom()` (wheel zoom about the cursor, drag to pan, double-click or Reset view to restore; nothing is clamped to the canvas edge). The walk also has a hover tooltip (artist, plays so far / total in this walk, tags) and click-to-seek: clicking a dot jumps to that artist's next play, wrapping to its first. The taste map keeps its own inline copy of the same logic.
- **Genre classification** (`genres.py`, tested by `test_genres.py`): the taste map's colours, legend and genre labels come from one genre per artist, not the raw first tag. `assign_genres()` merges tag synonyms into families (lofi / lo-fi / chillhop -> "lo-fi", country + americana/bluegrass -> "country", etc.), prefers the most specific qualifying genre over generic ones (pop, japanese, electronic) and keeps at most 40 genres, ranked by how many artists form the cluster (not minutes, so small-listening clusters survive). Artists with no usable tag borrow the weighted majority genre of their Last.fm neighbours (`gi: 1` marks those). The bundle carries `genres` (names ordered by minutes) and each artist's index in `g`. Genre labels are drawn on top of the dots with an outline, largest clusters first, and artist names avoid them.
- **Genre labels appear when relevant**: a genre's name is drawn only once >= 3 of its artists (and >= 15% of them) are lit at the current animation date (heard so far, or active in the last 30 days in that mode), fading in as the cluster fills. Labels are placed largest-priority first (compact, populous clusters), sized by cluster size, and a blocked label shifts up/down a notch before being dropped; zooming in reveals the rest.
- **Fullscreen is a viewing mode**: under `.chart-card:fullscreen` / `.is-fullscreen` the card becomes a dark grid (picture fills the screen; then a one-line legend; then a bar with Play/Restart/Reset view/exit beside a slim slider and its date ticks). All settings (selects, filters, date inputs, titles, notes, lists) are hidden there, and buttons/sliders are restyled to the visualization's dark palette (`#12061f`). Per-slider `#id` rules from the normal view are overridden with `!important` on width/margin.
- **Reactive genre labels** (`tasteMap.zoneMode = "reactive"`, the "Genre labels" dropdown): each genre gets a score from its share of the last 30 days of listening at the displayed date (square-rooted, normalised to the busiest genre, cached per day in `data.zoneCache`). The score scales the label's opacity (idle genres fade to near-invisible), size (current ones grow), colour (the most current go white) and its priority when labels compete for space. *Steady* keeps the plain size/opacity rules.
- **Canvas fonts**: canvas text can only use fonts that are already loaded, so `redrawCanvases()` (bottom of `dashboard.js`) waits for Fraunces/Inter via `document.fonts` and redraws the line race, taste map, walk and compare canvases, and again on `loadingdone`. Without it the first resting frame used a fallback font and switched when playback redrew it.
- **Map layout modes** (`tasteMap.layoutMode`, "Layout" dropdown; `tasteRunSim()` / `tasteInputs()`): *similarity* uses only the Last.fm links, pruned to each artist's strongest 15 and with link strength divided by the smaller node degree (the d3 default; hubs otherwise collapse the map) plus a weak same-genre chain. *Anchored by genre* first lays out the genres themselves (a small force sim over genre-to-genre similarity, discs sized by member count), then arranges artists around their genre's anchor with the same link forces, so clusters are crisp by construction (less faithful: the genre assignment, not just similarity, decides where artists sit). Layouts are cached per mode in `tasteMap.layouts` and `localStorage` (`taste-layout:v3:<mode>:...`); switching rebuilds everything derived from coordinates.
- Genre-anchored layout strength: the pull toward a genre's anchor is 0.4, balancing genre clustering with similarity links.
- **Walk genre labels** (`walk.labels`, the walk's "Genre labels" dropdown): genre names are drawn on the daily walk's canvas for genres the walk has visited so far. *React to the walk* scores each genre by the last ~40 hops (weight halves every 8 plays, square-rooted against the busiest genre) and scales opacity, size and label priority with it, so the genre you are in is large and bright and ones you left fade; *steady* shows every visited genre at one strength; *off* hides them. Labels use the genre colours and avoid overlapping each other (blocked ones nudge up/down).
